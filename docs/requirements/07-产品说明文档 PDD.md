## 2. 产品定位

### 2.1 是什么

> **知勤**是一套面向小型团队的轻量级人脸识别考勤管理系统，全本地化部署，纯浏览器即可运行，无需专用考勤硬件。

### 2.2 解决什么问题

| 当前痛点 | 知勤的解决方案 |
|----------|----------------|
| 纸质签到易代签、数据难追溯 | 人脸自动识别 + 时间戳 + 原始记录保留 |
| 月末考勤统计耗时长、易出错 | 自动记录 + 一键 CSV 导出 |
| 异常考勤缺乏实时感知和核实闭环 | 实时总览 + 异常标记 + 核实备注 |
| 商业考勤系统贵、需云服务依赖 | 零成本（课程项目）+ 全本地化 + H2 文件数据库 |

### 2.3 核心价值主张

> **"让考勤从手工登记 → 自动识别 → 数据可追溯全链路打通。"**

### 2.4 差异化定位

| 维度 | 知勤 | 商业产品（钉钉/企微） | 专用硬件（中控 Face ID） |
|------|------|----------------------|------------------------|
| 部署方式 | 单机 JAR + 浏览器 | SaaS 云端 | 硬件设备 |
| 数据位置 | 本地 H2 文件 | 云端 | 硬件本地 |
| 硬件需求 | 任意带摄像头的电脑 | 手机/电脑 | 专用考勤机 |
| 成本 | 免费 | SaaS 订阅 | 硬件采购 |
| 活体检测 | ❌ 无 | ✅ | ✅ |
| 排班/请假 | ❌ 无 | ✅ | ✅ |
| 员工自助 | ❌ 无 | ✅ | ❌ |

**知勤适用场景**：课程演示、小型工作室、内部小团队、无复杂排班的固定工作制场景。

## 4. 关键业务规则

> 以下规则是系统不可逾越的业务红线，任何实现必须遵守。

### 4.1 打卡规则

| 规则 | 描述 |
|------|------|
| **一次一签** | 每人每天仅允许一次签到（`attendance_date` 唯一） |
| **签退前置签到** | 必须先签到才能签退 |
| **一次一退** | 已签退后不可重复签退 |
| **时间判断** | 签到晚于上班时间 → "迟到"；签退早于下班时间 → "早退" |
| **识别阈值** | 默认 0.50，管理员可配置（0.30-0.60） |
| **模糊匹配保护** | 次优匹配距离与最优差距 < 0.05 时拒绝 |
| **多人脸拒绝** | 画面中非 1 张人脸时拒绝 |
| **停用人员拒绝** | `active = FALSE` 的人员不可打卡 |

### 4.2 数据完整性规则

| 规则 | 描述 |
|------|------|
| **原始状态不修改** | 核实异常时 `status` 字段保持原值，仅写 `note` |
| **演示/真实隔离** | 种子数据 `demo = TRUE`，真实人员 `demo = FALSE` |
| **时间戳锁定** | 打卡时间以 `LocalDateTime.now(Asia/Shanghai)` 为准 |
| **事务保护** | 人脸录入、打卡、核实均在事务中执行 |

### 4.3 安全规则

| 规则 | 描述 |
|------|------|
| **密码不明文** | BCrypt 编码后存入内存 `InMemoryUserDetailsManager` |
| **CSRF 必填** | 所有 POST/PATCH 必须带 CSRF Token |
| **API 无重定向** | `/api/*` 未登录返回 401 JSON，不跳转登录页 |
| **原始照片不持久化** | 仅存 128 维 JSON 描述符 |
| **默认 localhost** | `BIND_ADDRESS=127.0.0.1`，公网需显式修改 |

## 5. 术语表

| 术语 | 定义 |
|------|------|
| **Descriptor** | 128 维浮点向量，代表一张人脸的特征描述 |
| **Euclidean Distance（欧氏距离）** | 两个 Descriptor 之间的几何距离，越小表示两张脸越相似 |
| **TinyFaceDetector** | 轻量人脸检测器，从视频帧中定位人脸位置 |
| **Landmark 68** | 68 个人脸关键点定位（眼、鼻、嘴、下巴轮廓） |
| **Face Recognition Net** | 将关键脸区域编码为 128 维 Descriptor 的网络 |
| **CSRF** | 跨站请求伪造，Spring Security 默认防护机制 |
| **BCrypt** | 自适应哈希算法，Spring Security 推荐的密码编码方式 |
| **H2 Database** | Java 嵌入式数据库，文件模式下数据持久化到磁盘 |
| **SPEC 编程** | Specification-based Programming，先写需求规格再编码的方法 |
| **MVP** | Minimum Viable Product，最小可行产品 |

## 6. 假设与约束

| 编号 | 类型 | 描述 |
|------|------|------|
| A-01 | 假设 | 所有用户有基础浏览器操作能力 |
| A-02 | 假设 | 摄像头硬件正常、光线充足（720p+，均匀光线） |
| A-03 | 假设 | 管理员知晓并同意为员工采集人脸特征 |
| A-04 | 假设 | 打卡场景受监督（有人值守，无伪造风险） |
| A-05 | 假设 | 单机部署，数据量不超过数百人 + 一年考勤记录 |
| C-01 | 约束 | Java 17 + Spring Boot 3.5.7，不可切换版本 |
| C-02 | 约束 | 前端纯原生 HTML/CSS/JS，不引入 React/Vue |
| C-03 | 约束 | 人脸识别库锁定 face-api.js v1.7.15 |
| C-04 | 约束 | 数据库锁定 H2 文件模式，不可切换 PostgreSQL/MySQL |
| C-05 | 约束 | 课程周期内完成，迭代 1 优先保证功能闭环 |
| C-06 | 约束 | 所有时间按 Asia/Shanghai 时区 |
