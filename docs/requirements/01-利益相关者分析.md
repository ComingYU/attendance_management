# 利益相关者分析（Stakeholder Analysis）

> 本文档识别项目所有利益相关者，明确各方诉求与影响力，为后续需求协同奠定基础。

---

| 编号 | 角色 | 组织/身份 | 影响力 | 关注度 | 利益诉求 |
|------|------|-----------|--------|--------|----------|

## 2. 核心利益相关者深度画像

### SK-02 系统管理员（主要用户）

- **使用场景**：每日打开系统查看考勤总览，每月导出考勤报表，人员变动时新增/停用员工
- **痛点**：
  - 纸质签到容易代签，考勤造假难追溯
  - 月末统计考勤数据工作量大，容易出错
  - 异常考勤（迟到/早退/缺勤）缺乏实时感知
- **核心需求**：
  - 🎯 **打卡便捷可信**：人脸自动识别，无需手工操作
  - 🎯 **数据实时可见**：当日签到状态一目了然
  - 🎯 **异常可追溯**：异常记录可附核实说明，保留原始数据
  - 🎯 **报表可导出**：按月/按部门导出标准格式报表

### SK-03 企业员工（次要用户）

- **使用场景**：上下班时走到摄像头前完成打卡，无需额外操作
- **核心需求**：
  - 🎯 **快速打卡**：1-2 秒内完成识别
  - 🎯 **一次一签**：同一天不允许重复签到/签退
  - 🎯 **隐私保护**：原始照片不保存，仅存储特征向量

### SK-01 课程导师（决策相关者）

- **关注点**：
  - 是否经历完整的软件工程过程（需求 → 设计 → 编码 → 测试）
  - 文档是否规范、可追溯
  - 系统是否可独立运行并展示演示效果
  - 是否有版本迭代意识（而非一次性堆功能）

## 3. 利益冲突与协调策略

| 冲突方 | 冲突描述 | 协调策略 |
|--------|----------|----------|
| 管理员 vs 员工 | 管理员希望收集更多数据以便审计，员工关心隐私 | 仅存储 128 维人脸特征向量，不保存原始照片；员工需知情同意后采集 |
| 课程要求 vs 开发周期 | 完整软件工程流程需要时间，课程周期有限 | 采用 SPEC 迭代方式，每个迭代产出可演示版本，文档与代码同步演进 |
| 功能完备 vs 系统简洁 | 管理员希望统计分析越细越好，员工希望打卡越简单越好 | 使用权限/角色分层（当前仅管理员角色），打卡界面专注单一任务 |

## 4. 目标用户

> **当前迭代的目标用户：系统管理员**
>
> 管理员是考勤系统的核心用户，所有管理功能（人员管理、规则配置、数据统计）均围绕管理员角色设计。员工角色在当前版本中不提供自助访问入口，仅作为被打卡对象存在。

| 维度 | 描述 |
|------|------|
| 角色 | 企业 HR 或行政人员 |
| 技术水平 | 一般，能使用浏览器进行日常办公 |
| 主要工作 | 人员入职/离职管理、每日考勤查看、每月考勤报表导出、异常核实 |
| 对系统的期待 | "简单、可靠、不用培训就能上手" |
