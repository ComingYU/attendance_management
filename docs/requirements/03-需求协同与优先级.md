# 需求协同与优先级排序（Requirement Alignment & Prioritization）

> 本阶段通过利益相关者会议对调研发现进行协同评审，采用 **MoSCoW 法则** + **价值/风险矩阵** 确定迭代优先级。

---

## 1. 协同过程记录

**会议时间**：2026-11-03
**参与角色**：课程导师、系统管理员、项目经理、开发团队、最终评估者（虚拟代表）
**会议形式**：需求评审会议（2 小时）

### 1.1 协同原则

1. **单一交付物优先**：每个迭代必须产出可运行、可演示的版本
2. **MVP 聚焦核心流程**：先跑通"打卡 → 记录 → 查看"完整链路
3. **技术债务显性化**：当前版本不做但未来需要的功能必须记录，不得"遗忘"
4. **课程评估对齐**：必须覆盖软件工程课程的能力考核点

### 1.2 争议点与决议

| 争议点 | 各方意见 | 最终决议 |
|--------|----------|----------|
| 是否支持排班管理 | 管理员：需要；导师：增加复杂度 | ❌ 暂不支持，单班次，记录为 NFR-未来需求 |
| 是否支持多管理员/角色 | 导师：应体现 RBAC；开发：复杂度高 | ⚠️ v1.0 单管理员，v1.1 考虑角色扩展 |
| CSV vs Excel 导出 | 管理员：Excel 好；开发：CSV 简单 | ✅ CSV（UTF-8 BOM），Excel 可直接打开 |
| 是否需要活体检测 | 导师：安全第一；开发：课程难度大 | ❌ 明确标注"适用于受监督演示场景"，技术边界写入文档 |
| 演示数据是否保留 | 管理员：初始环境为空；导师：演示用 | ✅ `SEED_DEMO` 环境变量控制，默认生成演示数据 |

## 2. MoSCoW 优先级排序

### 2.1 Must Have（必须有）— 迭代 1

| 编号 | 需求 | 来源 |
|------|------|------|
| M-01 | 管理员登录（用户名 + 密码） | 安全基础 |
| M-02 | 新增/停用人员（工号唯一） | 人员管理基础 |
| M-03 | 人脸录入（带重复检查） | 核心功能 |
| M-04 | 人脸打卡（签到 + 签退） | 核心功能 |
| M-05 | 识别匹配不到时拒绝打卡 | 核心安全 |
| M-06 | 考勤总览（今日应到/出勤/异常） | 管理基础 |
| M-07 | 考勤记录查询与筛选 | 管理基础 |
| M-08 | 上/下班时间 & 识别阈值可配置 | 规则灵活 |
| M-09 | 异常考勤核实（保留原始状态） | 数据可追溯 |
| M-10 | CSV 报表导出 | 月末汇总 |

### 2.2 Should Have（应该有）— 迭代 2

| 编号 | 需求 | 说明 |
|------|------|------|
| S-01 | 近 7/30 天考勤趋势图 | 管理员希望看到趋势 |
| S-02 | 部门考勤分布分析 | 跨部门对比管理 |
| S-03 | 人脸识别匹配距离显示 | 让管理员了解识别准确度 |
| S-04 | 多个人脸同时出现时拒绝 | 防误识别增强 |

### 2.3 Could Have（可以有）— 迭代 3+

| 编号 | 需求 | 说明 |
|------|------|------|
| C-01 | 人脸重新录入覆盖旧特征 | 员工整容/戴眼镜更新档案 |
| C-02 | 管理员密码修改 | 安全运维 |
| C-03 | 数据备份/恢复功能 | H2 文件复制 |

### 2.4 Won't Have（暂不考虑）

| 编号 | 需求 | 说明 |
|------|------|------|
| W-01 | 排班管理 | 超出课程范围 |
| W-02 | 请假/加班审批 | 超出课程范围 |
| W-03 | 员工自助账号 | 无角色体系支撑 |
| W-04 | 活体检测 | 技术复杂度高，边界已声明 |
| W-05 | 移动端 App | 纯 Web 技术栈聚焦 |
| W-06 | 云端部署 / 多租户 | 单机部署场景 |

## 3. 价值/风险矩阵

```
  高价值
    ↑
    │  M-03 人脸录入      M-01 登录
    │  M-04 人脸打卡      M-02 人员管理
    │  M-05 识别拒绝      M-06 考勤总览
    │  (核心闭环)         (管理基础)
    │
    │  M-09 异常核实      M-07 记录查询
    │  M-10 CSV 导出      M-08 规则配置
    │  S-01 趋势图        S-02 部门分析
    │
    └──────────────────────→ 高风险
         低风险
```

> **风险评估维度**：技术复杂度、安全风险、对后续迭代的阻塞影响。

| 模块 | 价值 | 风险 | 迭代 | 选入依据 |
|------|------|------|------|----------|
| 登录认证 | 高 | 低 | 迭代 1 | 所有 API 的前置条件 |
| 人员管理 | 高 | 低 | 迭代 1 | 人脸录入的前置条件 |
| 人脸录入+打卡 | 极高 | 中 | 迭代 1 | **核心价值，必须跑通** |
| 考勤记录+查询 | 高 | 低 | 迭代 1 | 打卡的产出，即时可见 |
| 规则配置 | 高 | 低 | 迭代 1 | 迟到/早退判断依赖 |
| 异常核实 | 高 | 低 | 迭代 1 | 数据追溯闭环 |
| CSV 导出 | 中 | 低 | 迭代 1 | 课程能力点覆盖 |
| 统计图表 | 中 | 低 | 迭代 2 | 产品加分项 |

## 4. 迭代范围锁定

### 迭代 1（V1.0 交付）— 核心闭环

> **目标**：跑通"登录 → 建人 → 录脸 → 打卡 → 记录 → 导出"全流程，可独立演示。

包含：M-01 至 M-10

### 迭代 2（V1.1 交付）— 体验增强

> **目标**：数据可视化、识别体验优化。

包含：S-01 至 S-04 + 迭代 1 的 Bug 修复

### 迭代 3（V1.2 交付）— 运维增强

> **目标**：管理员自助运维功能。

包含：C-01 至 C-03

---

## 5. 验收门控（Definition of Done）

每个迭代完成时必须通过以下检查：

| 门控项 | 说明 |
|--------|------|
| ✅ 功能完整性 | 所有 Must Have 需求可运行 |
| ✅ 测试覆盖 | 核心业务流程有自动化测试 |
| ✅ 文档同步 | 需求/设计/测试文档版本一致 |
| ✅ 演示就绪 | 一键启动脚本、演示数据准备完毕 |
| ✅ 安全检查 | CSRF 保护、密码 BCrypt、未登录 API 返回 401 |
| ✅ 边界声明 | 非目标功能（Won't Have）在文档中明确说明 |
