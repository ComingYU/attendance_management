## 1 研究背景与意义

### 1.1 研究背景

考勤管理是企业人力资源管理的基础环节，其效率和准确性直接关系到薪资核算、绩效考核和团队运营。传统考勤方式经历了从纸质签到、刷卡考勤、指纹考勤到人脸识别考勤的演进，每一次技术革新都试图解决前一代方案的痛点。

目前主流的人脸识别考勤方案（如钉钉考勤、企业微信考勤、中控 Face ID 等）大多依赖云服务或专用硬件设备，带来以下问题：

- **成本高企**：硬件采购成本 + 云端服务年费，对小型团队构成负担
- **数据隐私**：人脸特征数据上传第三方服务器，存在合规风险
- **部署复杂**：需要 IT 运维支持，不利于轻量快速启动

与此同时，浏览器端人脸识别技术（face-api.js、TensorFlow.js 等）在近两年迅速成熟，使得"纯浏览器运行、无需专用硬件、人脸特征本地提取"成为可能。这为本课题提供了技术基础和现实动因。

### 1.2 研究意义

本课题的研究意义体现在三个层面：

**（1）理论与方法层面**

探索浏览器端轻量级深度学习模型（TinyFaceDetector + Landmark68Net + FaceRecognitionNet）与后端业务系统的集成模式，研究"前端特征提取 + 后端欧氏距离匹配"的分布式人脸识别架构，为同类课程项目和小型应用提供可复用的技术范式。

**（2）工程实践层面**

完整遵循 SPEC（Specification-based Programming）编程方法，从利益相关者分析 → 需求调研 → OOA 三步建模 → SRS 规格说明书 → 迭代开发，展示一套面向小型项目的规范化软件工程流程。

**（3）应用价值层面**

产出一套名为"知勤"的人脸识别考勤管理系统——全本地化部署、纯浏览器运行、零外部依赖、零硬件采购，适合 500 人以下小型团队或课程演示场景，具有实际可用性。

## 2 国内外研究现状

### 2.1 人脸识别技术演进

人脸识别技术自 20 世纪 60 年代起步，经历了四个阶段：

| 阶段 | 时期 | 代表方法 | 准确率（LFW） |
|------|------|----------|--------------|
| 几何特征法 | 1960s–1990s | 眼距、鼻宽等人脸几何特征 | < 60% |
| 子空间方法 | 1990s–2000s | PCA（特征脸）、LDA | ~ 70% |
| 传统机器学习 | 2000s–2010s | SVM、AdaBoost + Haar Cascade | ~ 90% |
| 深度学习 | 2012 至今 | DeepFace、FaceNet、ArcFace | > 99% |

当前主流深度学习方案采用**三元组损失函数**（Triplet Loss）训练卷积神经网络，将人脸映射到 128 维或 512 维欧氏空间，通过距离阈值判断身份。FaceNet（Google, 2015）首次公开了 128 维描述符方案，本项目采用的 FaceRecognitionNet 即属此路线。

### 2.2 浏览器端人脸识别技术

浏览器端人脸识别主要依赖两条技术路线：

| 库 | 底层框架 | 特点 |
|----|----------|------|
| **face-api.js** | TensorFlow.js | MIT 协议，封装了 3 个预训练模型，本项目采用 |
| **MediaPipe Face Mesh** | Google TFLite | Google 出品，侧重 468 点网格 |
| **OpenCV.js** | Emscripten 编译 | 传统算法移植，无深度学习模型 |

face-api.js v1.7.15 提供的三个预训练模型在 NVIDIA GeForce 940M GPU 上达到约 30 FPS，CPU 上约 3–5 FPS，满足考勤打卡"单次识别 ≤ 2 秒"的体验要求。原始模型文件总大小约 14 MB，首次加载约 4 秒。

### 2.3 考勤系统相关研究

| 方案 | 架构 | 数据源 | 本地化 | 成本 |
|------|------|--------|--------|------|
| 钉钉考勤 | 云服务 + App | 云端 | ❌ | 年费 |
| 企业微信考勤 | 云服务 + App | 云端 | ❌ | 年费 |
| 中控 Face ID | 专用硬件 + 云端可选 | 本地/云端 | ✅（硬件） | 硬件采购 |
| **本项目"知勤"** | **浏览器 + Spring Boot** | **本地 H2** | **✅** | **零成本** |

本项目的差异化定位：轻量级、全本地化、纯 Web、无硬件、零成本填补了小型团队人脸识别考勤的市场空白。

## 3 研究内容与目标

### 3.1 研究内容

本课题围绕"知勤"考勤系统展开，具体研究内容包括：

**（1）浏览器端人脸识别集成**

研究 face-api.js 三个预训练模型（TinyFaceDetector 检测 → Landmark68Net 对齐 → FaceRecognitionNet 编码）的加载、初始化、摄像头帧处理与 128 维特征描述符提取流程，解决纯浏览器环境下的实时识别问题。

**（2）后端欧氏距离匹配算法设计**

设计遍历式距离比对方案：对所有在职已录脸人员逐一计算欧氏距离，取最优（最小距离）和次优记录，通过阈值判断（0.30–0.60 可配置）和模糊保护（次优 − 最优 < 0.05 时拒绝）实现可靠匹配。

**（3）考勤业务逻辑建模**

建模签到/签退互斥规则、迟到/早退自动判断、异常核实闭环（核实说明不可修改原始状态）、停用人员禁止打卡等核心业务逻辑，并用 `@Transactional` 事务 + `FOR UPDATE` 行锁保证并发安全。

**（4）Spring Boot 单体应用架构**

采用 Java 17 + Spring Boot 3.5.7 + Spring Security + JDBC + H2 嵌入式数据库的极简技术栈，实现 REST API 与同源静态资源服务的一体化部署。

**（5）规范化软件过程实践**

完整执行 SPEC 编程方法：利益相关者分析 → 需求调研 → Story 列表 → 用例建模 → OOA 三步建模（场景建模、静态建模、行为建模）→ SRS 规格说明书 → 迭代开发。

### 3.2 研究目标

**总体目标**：设计并实现一套"知勤"人脸识别考勤管理系统，达到以下验收标准：

| 编号 | 目标 | 量化指标 |
|------|------|----------|
| G-01 | 人脸打卡全链路可演示 | 登录 → 建人 → 录脸 → 打卡 → 记录 → 导出，26 个验收场景全部通过 |
| G-02 | 识别性能达标 | 后端特征匹配响应 ≤ 1 秒（500 人规模），前端首次模型加载 ≤ 5 秒 |
| G-03 | 安全防护到位 | CSRF Token 强制校验、BCrypt 密码编码、Session 60 分钟超时、API 未登录返回 401 |
| G-04 | 代码质量可控 | 后端核心类单文件 ≤ 150 行，集成测试 ≥ 6 条核心流程，测试通过率 100% |
| G-05 | 一键启动部署 | Windows PowerShell 两条脚本即可完成模型下载和服务启动 |

### 3.3 研究范围与边界

**纳入范围**：

- ✅ 单管理员角色的考勤管理全流程
- ✅ 浏览器端特征提取 + 后端欧氏距离比对
- ✅ 单班次（上班 09:00 / 下班 18:00，可配置）
- ✅ 异常考勤核实与 CSV 报表导出
- ✅ 考勤总览、趋势、分布的数据统计

**明确不做**：

- ❌ 活体检测（照片重放风险，文档标注边界）
- ❌ 多管理员分权、员工自助账号（无 RBAC 体系）
- ❌ 排班/请假/加班/节假日管理
- ❌ 移动端 App、云端部署、多租户
- ❌ 人脸特征加密存储（课程范围）

### 4.3 人脸识别核心算法流程

```
摄像头帧输入 (640×480)
        │
        ▼
┌───────────────────┐
│ TinyFaceDetector   │  ← 轻量级人脸检测
│ 输出: bbox 数组     │
└─────────┬─────────┘
          │ 过滤: 必须且仅能有 1 张人脸
          ▼
┌───────────────────┐
│ Landmark68Net      │  ← 68 点关键点定位 (对齐)
│ 输出: 68 个 (x,y)  │
└─────────┬─────────┘
          │
          ▼
┌─────────────────────┐
│ FaceRecognitionNet    │  ← 128 维特征编码
│ 输出: double[128]     │
└─────────┬───────────┘
          │ POST JSON
          ▼
┌───────────────────────────────────────────────┐
│ 后端欧氏距离匹配算法                             │
│                                               │
│  for each active employee with descriptor:     │
│      d = sqrt(Σ(aᵢ − bᵢ)²)                    │
│      if d < best: { second = best; best = d }  │
│                                               │
│  三重校验:                                      │
│  ① best ≤ threshold (0.30–0.60 可配置)          │
│  ② second − best ≥ 0.05 (模糊保护)              │
│  ③ 人员 active = TRUE                          │
└───────────────────────────────────────────────┘
```

| note | VARCHAR(300) | 可空 | 核实说明 |

**表 3：settings（规则配置表）**

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | INT | PK, 固定值 1 | 单例设计 |
| start_time | VARCHAR(5) | HH:mm | 上班时间，默认 09:00 |
| end_time | VARCHAR(5) | HH:mm | 下班时间，默认 18:00 |
| threshold | DOUBLE | [0.30, 0.60] | 欧氏距离阈值，默认 0.50 |

**数据完整性规则**：

| 规则 | 实现方式 |
|------|----------|
| 工号全局唯一 | `UNIQUE` 约束 |
| 每人每天唯一考勤记录 | `UNIQUE(employee_id, attendance_date)` |
| 考勤记录引用有效员工 | `FOREIGN KEY employee_id REFERENCES employees(id)` |
| 事务保护 | `@Transactional` + `FOR UPDATE` 行锁 |

### 5.4 核心业务流程设计

#### 5.4.1 人脸打卡签到/签退流程

```
管理员选择 "上班签到" 或 "下班签退"
        │
        ▼
摄像头预览 → 管理员点击 "开始识别"
        │
        ▼
浏览器提取 128 维描述符
        │ POST /api/recognize
        ▼
后端: 遍历所有在职已录脸人员
        │
        ▼
计算欧氏距离 → 找 best 和 second
        │
   ┌────┴────┐
   │ 三重校验 │
   └────┬────┘
        │
   ┌────┴────────────────────────────┐
   │                                 │
全部通过                          任一不通过
   │                                 │
   ▼                                 ▼
   根据 action 判断签到或签退        返回 400 + 错误提示
   │
   ├─ action="in":
   │    查询今日记录是否存在
   │    ├─ 存在 → 拒绝 "今日已签到"
   │    └─ 不存在 → INSERT
   │         status = now > start_time ? "迟到" : "正常"
   │
   └─ action="out":
        查询今日记录
        ├─ 不存在 → 拒绝 "请先完成上班签到"
        ├─ check_out 不为空 → 拒绝 "今日已签退"
        └─ 存在且未签退 → UPDATE check_out 和 status
             status = 原 status + (now < end_time ? "早退" : "")
```

#### 5.4.2 异常核实闭环流程

```
考勤记录 status ≠ "正常" 且 resolved = FALSE
        │
        ▼
管理员填写 1–300 字核实说明
        │ POST /api/records/{id}/resolve
        ▼
后端:
  UPDATE attendance
  SET resolved = TRUE, note = ?
  WHERE id = ? AND status <> '正常' AND resolved = FALSE
        │
   ┌────┴────┐
   │ 影响行数  │
   └────┬────┘
        │
   ┌────┴────┐
   │         │
   = 1       = 0
   │         │
   ▼         ▼
 成功        拒绝
            (已处理或无需处理)

⚠ 关键约束: status 字段在任何核实操作中不可修改
```

### 5.5 安全设计

| 维度 | 方案 | 实现位置 |
|------|------|----------|
| **认证** | Spring Security 表单登录 + Session（60 分钟超时） | `SecurityConfig.java` |
| **密码** | BCrypt 编码，管理员凭证通过环境变量 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 配置，不存数据库 | `InMemoryUserDetailsManager` |
| **CSRF** | 所有 POST / PATCH / PUT 请求强制 Token 校验 | Spring Security Filter Chain |
| **API 鉴权** | 自定义 EntryPoint：未登录访问 `/api/*` 返回 401 JSON，不返回重定向 | `SecurityConfig.java` |
| **端口绑定** | 默认仅监听 `127.0.0.1`，公网访问需显式修改 `BIND_ADDRESS` | `application.properties` |
| **异常屏蔽** | `server.error.include-message=never`，不暴露堆栈 | 配置文件 |
| **隐私边界** | 原始人脸照片不上传、不持久化，仅存 128 维描述符 CLOB | 数据库设计 |
| **并发安全** | `@Transactional` + `FOR UPDATE` 行锁防止重复签到 | `AttendanceService.recognize()` |

### 5.6 性能设计

| 指标 | 目标 | 设计保障 |
|------|------|----------|
| 后端匹配响应 | ≤ 1 秒（500 人规模） | 描述符已存内存上下文，遍历计算 500×128 次浮点运算 ≤ 1 ms |
| 首次模型加载 | ≤ 5 秒 | face-api.js 三个模型约 14 MB，localhost 直传 |
| 系统启动 | ≤ 15 秒 | Spring Boot 3 + H2 文件模式，无外部连接 |
| 并发控制 | 防重复签到 | `FOR UPDATE` 行锁 + `UNIQUE(employee_id, attendance_date)` |

## 8 可能遇到的问题与解决方案

| 编号 | 问题 | 影响 | 解决方案 |
|------|------|------|----------|
| PRB-01 | 人脸识别准确率受光线影响大 | 识别失败率上升 | 在打卡界面明确提示光线要求（> 200 lux），管理员可通过环境变量调整阈值 |
| PRB-02 | face-api.js 在旧浏览器不支持 | 无法使用 | 明确声明仅支持 Chrome / Edge 最新版，不支持 IE / Safari |
| PRB-03 | 首次模型下载需联网（~14 MB） | 离线环境无法启动 | `download-models.ps1` 脚本提供本地路径模式支持 |
| PRB-04 | 欧氏距离阈值难以精确校准 | 识别过松或过严 | 提供 0.30–0.60 可配置范围，默认 0.50，并提供"模糊保护"兜底机制 |
| PRB-05 | 照片重放 / 伪造描述符风险 | 安全边界 | 在 README 和 SRS 中明确声明"无活体检测，仅用于受监督演示"，生产环境需升级 |
| PRB-06 | H2 数据库并发能力有限 | 多人同时打卡冲突 | `FOR UPDATE` 行锁 + `UNIQUE` 约束，单机 ≤ 500 人规模下够用 |
| PRB-07 | CSV 导出中文 BOM 不兼容 | Excel 打开乱码 | 已实现 UTF-8 BOM（`\uFEFF`），兼容 Excel 2016+ |
